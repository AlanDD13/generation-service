# Сервис генерации

Python 3.12, FastAPI, PostgreSQL 17, SQLAlchemy и Alembic.

## Запуск

Нужны Docker и Docker Compose. Из корня проекта:

```sh
docker compose up --build -d
```

Команда поднимает базу, применяет миграции, запускает сервис с четырьмя
воркерами Uvicorn и провайдеров alpha и beta.

- API сервиса: http://localhost:8000/docs
- Alpha: http://localhost:8001/docs
- Beta: http://localhost:8002/docs

Миграция добавляет каталог из задания и пользователя `1` с нулевым балансом.
Начисление через `POST /webhooks/payments` выполняется для `status=succeeded`.
Вебхуки подписываются HMAC-SHA256 сырых байтов тела; заголовок `X-Signature`
содержит подпись в hex. Общий секрет — `WEBHOOK_SECRET`, по умолчанию
`local-development-secret`. Пример переменных — в `.env.example`.

Настройки каждого фейка меняются через `PUT /settings` и читаются через
`GET /settings`:

- `failure_rate` от 0 до 1 и `error_type`: technical, moderation, payload;
- `sync_mode`: normal, 503, timeout;
- `delay_min`, `delay_max`: задержка вебхука, по умолчанию 2–20 секунд;
- `duplicate_webhook`, `concurrent_duplicates`: повторная доставка;
- `no_webhook`: не отправлять результат.

`PUT /settings` заменяет настройки, пропущенные поля получают значения по
умолчанию. Для позднего результата задайте задержку больше `PROVIDER_TIMEOUT`.
По умолчанию он равен 60 секундам. При изменении времён должно выполняться
`HTTP_TIMEOUT < DISPATCH_LEASE < PROVIDER_TIMEOUT`.

## Тесты

После запуска стенда:

```sh
docker compose --profile test run --rm --build tests
```

Набор проверяет четыре обязательных сценария:

1. 20 одновременных одинаковых оплат дают одно начисление.
2. 10 одновременных отказов последней ноги дают один возврат.
3. После отказа первой ноги заказ завершается на второй, в истории две попытки.
4. Поздний completed после сторожа не меняет завершённый заказ.

Тесты используют настоящий PostgreSQL и HTTP-сервис с четырьмя воркерами.
Проверки логики очищают отдельную базу `generation_test`. E2E-тесты создают
уникальных пользователей в рабочей базе стенда, временно меняют настройки
фейков и восстанавливают их после выполнения. Запускайте набор последовательно
на локальном стенде без ручных заказов.

## Миграции

При запуске compose миграции применяются отдельным контейнером до старта
приложений. Применить вручную:

```sh
docker compose run --rm migrate
```

Для добавления следующей миграции нужны Python 3.12+ и uv. После изменения
ORM-моделей при работающей базе compose:

```sh
uv sync --frozen
uv run alembic revision --autogenerate -m add_model_field
uv run alembic upgrade head
uv run alembic check
```

Перед применением проверьте сгенерированные `upgrade` и `downgrade`.
Для миграции данных создайте пустой revision через
`uv run alembic revision -m add_catalog_model` и заполните его вручную.

## Ровно один раз для начисления и возврата

Баланс вычисляется как сумма `ledger_entries.amount`. Отдельного изменяемого
баланса нет; каждое начисление, списание и возврат — строка журнала.

Начисление защищено `UNIQUE(payment_id)` и `INSERT ... ON CONFLICT DO NOTHING`.
Повтор с теми же реквизитами не добавляет запись. Другой пользователь или сумма
уже начисленного payment_id дают 409.

Списание и возврат защищены `UNIQUE(task_id, operation_type)`: для одного заказа
допускается не более одной записи debit и одной refund. Создание заказа, списание и первая
попытка сохраняются одной транзакцией.

Финансовые операции сначала блокируют строку пользователя. Переходы задачи
блокируют пользователя, заказ и попытку, затем заново проверяют состояние.
Окончательный отказ и возврат фиксируются одной транзакцией. Повторные вебхуки
и конкурирующие сторожа не повторяют переход или возврат.

Гарантия относится к денежному эффекту в PostgreSQL. HTTP-сообщения могут
доставляться повторно.

## Падение процесса и поздний результат

Если процесс остановился до commit вебхука, незавершённые изменения откатываются.
Если commit прошёл, но ответ 200 потерялся, повторное сообщение увидит уже
обработанную оплату или попытку и не повторит эффект.

Попытки служат устойчивой очередью отправки в PostgreSQL. Воркеры получают
работу через `FOR UPDATE SKIP LOCKED` и временную аренду. После остановки
отправителя другой воркер повторит запрос по истечении аренды, если дедлайн
попытки ещё не прошёл; иначе попытку закроет сторож. HTTP выполняется вне
транзакции. Повтор использует тот же attempt_id как `Idempotency-Key`;
фейк возвращает прежний external_id. Токен аренды не позволяет старому
отправителю перезаписать состояние после нового захвата.

Вебхук, синхронная ошибка отправки и сторож используют общий переход отказа:
следующая подходящая нога либо окончательный failed с единственным возвратом.

**Правило 6:** результат закрытой попытки игнорируется с ответом 200, даже если
заказ ещё выполняется на следующей ноге. После возврата completed также
не принимается. При гонке результата со сторожем побеждает первый
зафиксированный переход под блокировками. Если дедлайн уже прошёл, но сторож
ещё не закрыл попытку, completed может быть принят.
