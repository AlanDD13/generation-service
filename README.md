# Сервис генерации

FastAPI, PostgreSQL, асинхронный SQLAlchemy и Alembic. Сервис принимает заказ,
списывает токены, перебирает подходящие ноги модели и возвращает списанное,
если выполнить заказ не удалось. `alpha` и `beta` — два экземпляра одного
приложения фейкового провайдера.

## Запуск

Нужны Docker и Docker Compose. Из корня проекта:

```sh
docker compose up --build -d
docker compose ps
```

Поднимаются PostgreSQL 17, одноразовый контейнер миграций, API с четырьмя
воркерами Uvicorn и оба провайдера. Миграции завершаются до запуска приложений.

| Адрес | Назначение |
| --- | --- |
| http://localhost:8000/docs | API сервиса |
| http://localhost:8000/health | Проверка соединения с базой |
| http://localhost:8001/docs | Провайдер alpha |
| http://localhost:8002/docs | Провайдер beta |
| localhost:55432 | PostgreSQL: база, пользователь и пароль `generation` |

Порты опубликованы только на localhost. Секрет по умолчанию —
`local-development-secret`; его можно переопределить через `WEBHOOK_SECRET`
в окружении или `.env`. Это локальная конфигурация для тестового задания.

Миграция создаёт пользователя `1` с нулевым балансом и каталог:

| Модель | Цена | Ноги |
| --- | --- | --- |
| image-fast | 2 | alpha: до 4 референсов → beta: до 10 |
| video-long | 25 | beta: до 2 → alpha: до 1, пропускается после moderation |

Пополнить баланс подписанным вебхуком можно без локальной установки Python:

```sh
docker compose exec -T service .venv/bin/python - <<'PY'
import hashlib
import hmac
import json
import os
import uuid

import httpx

body = json.dumps({
    "payment_id": str(uuid.uuid4()),
    "user_id": 1,
    "tokens": 100,
    "status": "succeeded",
}).encode()
signature = hmac.new(
    os.environ["WEBHOOK_SECRET"].encode(), body, hashlib.sha256
).hexdigest()
response = httpx.post(
    "http://localhost:8000/webhooks/payments",
    content=body,
    headers={"X-Signature": signature, "Content-Type": "application/json"},
)
print(response.status_code, response.text)
PY
```

Создать заказ и посмотреть баланс:

```sh
curl -s http://localhost:8000/generate \
  -H 'Content-Type: application/json' \
  -d '{"user_id":1,"model_slug":"image-fast","prompt":"A quiet sea","ref_images":[]}'
curl -s http://localhost:8000/users/1/balance
```

Первый запрос возвращает `202 {"task_id":"..."}`. Полученный UUID подставляется
в `GET /tasks/{task_id}`. Обычный провайдер присылает результат через 2–20 секунд.
Результат — строка-ссылка; файл по ней не создаётся.

Другого пользователя можно добавить SQL-запросом, без регистрации:

```sh
docker compose exec db psql -U generation -d generation \
  -c 'INSERT INTO users (id) VALUES (2)'
```

Логи и остановка с сохранением данных:

```sh
docker compose logs -f service alpha beta
docker compose down
```

## API и принятые соглашения

- `POST /generate`: `user_id`, `model_slug`, `prompt`, необязательный список
  `ref_images`. Нет подходящей ноги — 400 до списания; не хватает токенов — 402;
  уже три активные задачи — 429. Неизвестная модель или пользователь — 404.
- `GET /tasks/{id}`: статус, `current_leg` с именем провайдера, идентификатор
  текущей попытки, результат и история попыток. После завершения `current_leg`
  обозначает последнюю испробованную ногу.
- `GET /users/{id}/balance`: сумма журнала и последние 20 операций, новые первыми.
- `POST /webhooks/payments`: `payment_id`, `user_id`, положительное целое `tokens`,
  `status`. Начисление выполняется только для `succeeded`; `pending` и `failed`
  подтверждаются без изменения баланса. Одинаковый успешный платёж можно
  повторять. Другие реквизиты уже начисленного `payment_id` дают 409.
- `POST /webhooks/providers/{name}`: тело вида ниже. Ошибочная подпись — 401,
  неверное тело — 422, несоответствие провайдера или известного `external_id` — 409.

```json
{
  "attempt_id": "UUID попытки",
  "external_id": "идентификатор провайдера",
  "status": "completed",
  "result_url": "https://files.example/result.png"
}
```

Для отказа вместо `result_url` передаются `"status":"failed"` и
`"error_type":"technical"`, `"moderation"` или `"payload"`.

Оба вида вебхуков подписаны одинаково: `X-Signature` содержит шестнадцатеричный
HMAC-SHA256 исходных байтов тела. После подписания нельзя пересериализовывать JSON:
пробелы и порядок ключей тоже входят в подпись. Сравнение выполняется через
`hmac.compare_digest`.

Статусы заказа: `pending`, `completed`, `failed`. В `pending` входят очередь,
отправка и ожидание вебхука. Статусы попытки: `queued`, `dispatching`,
`awaiting_webhook`, `completed`, `failed`, `timed_out`.

Каждый новый `POST /generate` — отдельный заказ. Повтор идентичного запроса
не считается повторной доставкой старого заказа. Идемпотентность клиентского
создания заказа не входит в этот API; повторная доставка платежей и результатов
провайдера поддерживается.

## Почему денежный эффект происходит ровно один раз

Баланс не хранится отдельным изменяемым числом. Он вычисляется как
`COALESCE(SUM(ledger_entries.amount), 0)`. Начисление — положительная строка,
списание — отрицательная, возврат — положительная. Поэтому отдельного изменения
баланса без записи в журнале в приложении нет. Журнал только пополняется;
приложение не редактирует и не удаляет его строки.

База обеспечивает независимую защиту от повторов:

| Операция | Ограничение |
| --- | --- |
| Начисление | `UNIQUE(payment_id)` |
| Списание | `UNIQUE(task_id, operation_type)`, тип `debit` |
| Возврат | то же ограничение, тип `refund` |
| Попытка конкретной ноги | `UNIQUE(task_id, leg_id)` |
| Активная попытка | частичный уникальный индекс по `task_id` |

Каждая денежная операция сначала блокирует строку пользователя через
`SELECT ... FOR UPDATE`. Проверка доступного баланса, лимита активных задач,
создание заказа и списание входят в одну транзакцию. Даже десять одновременных
запросов одного пользователя проверяют баланс последовательно.

Переходы задачи блокируют строки в порядке: пользователь → задача → попытка.
После получения блокировок обработчик заново проверяет статус и текущую попытку.
Повторный вебхук видит уже обработанное состояние и отвечает 200.

Для последнего отказа статус задачи, статус попытки и возврат фиксируются одной
транзакцией. Не существует зафиксированного состояния «задача упала, возврат ещё
предстоит сделать». Уникальное ограничение страхует от второго возврата.

Гарантия относится к эффекту в базе. Сетевые сообщения могут доставляться
повторно; доставка «ровно один раз» по HTTP здесь не предполагается.

## Отказы, сторож и поздний результат

Все источники отказов используют одну функцию `_fail`:

- `technical` ведёт к следующей подходящей ноге;
- `moderation` также исключает ноги с `skip_on_moderation`;
- `payload` сразу завершает заказ с возвратом;
- 5xx, сетевой таймаут и некорректный ответ на отправку считаются техническими
  отказами; остальные неожиданные HTTP-статусы также считаются техническими;
- превышение `PROVIDER_TIMEOUT` записывается как `timed_out`, тип `technical`,
  причина `provider_timeout`.

Фильтр референсов применяется при выборе каждой ноги. Неподходящие и пропущенные
ноги не создают фиктивные попытки в истории.

Сторож запущен в каждом из четырёх воркеров. Он находит просроченные попытки,
затем обрабатывает каждую под теми же блокировками, что и вебхук. Два сторожа
могут найти одну запись, но перейти к следующей ноге или вернуть токены сможет
только первый. Второй повторно проверит состояние и ничего не изменит.

**Решение для позднего `completed`: терминальное состояние попытки неизменно.**
После зафиксированного таймаута старый результат игнорируется с ответом 200,
даже если следующая нога ещё работает. После возврата он также игнорируется.

Если сторож и `completed` пришли одновременно, побеждает первый зафиксированный
переход: либо результат без возврата, либо таймаут с дальнейшим fallback/возвратом.
Само наступление дедлайна ещё не меняет состояние: если сторож не успел
зафиксировать таймаут, завершение может быть принято. Это сознательная политика
разрешения гонки, а не проверка времени получения HTTP-запроса.

## Что происходит при падении процесса

| Момент падения | Восстановление |
| --- | --- |
| До commit вебхука | PostgreSQL откатывает всю транзакцию; повтор обработает событие |
| После commit, до ответа 200 | Повтор увидит обработанный платёж/попытку и не повторит эффект |
| После списания, до отправки | Попытка `queued` остаётся в PostgreSQL; её подберёт воркер |
| Во время отправки | После окончания аренды попытка снова доступна для отправки |
| Провайдер принял задание, ответ не сохранён | Повтор с тем же `attempt_id` вернёт прежний `external_id` |
| После принятия, до вебхука | Другие воркеры примут вебхук или сторож обработает дедлайн |

Таблица попыток служит устойчивой очередью: отдельной очереди в памяти нет.
Воркеры захватывают отправку через `FOR UPDATE SKIP LOCKED`, записывают аренду
и освобождают транзакцию **до** HTTP-запроса. Токен аренды не позволяет старому
отправителю перезаписать состояние после нового захвата.

Провайдер получает `Idempotency-Key`, равный `attempt_id`. Он сохраняет задания
в PostgreSQL с уникальностью `(provider, attempt_id)` и проверяет неизменность
запроса при повторе. Повторная отправка не создаёт новую генерацию у этого
провайдера и не продлевает исходный дедлайн.

Вебхук содержит внутренний `attempt_id`, поэтому может быть обработан даже
раньше сохранения ответа `202`. Позднее сохранение ответа не вернёт завершённую
попытку в ожидание.

Сетевой таймаут не доказывает, что провайдер не принял запрос. В режиме `timeout`
фейк специально принимает задание, но задерживает ответ. Сервис может перейти
к следующей ноге; результат прежней ноги тогда игнорируется. Идемпотентность
одной попытки не означает, что разные ноги не выполнят работу одновременно.

## Настройки провайдеров и времени

`GET /settings` и `PUT /settings` доступны на каждом фейковом провайдере.
`PUT` заменяет настройки; пропущенные поля получают значения по умолчанию.

```sh
curl -s -X PUT http://localhost:8001/settings \
  -H 'Content-Type: application/json' \
  -d '{"failure_rate":1,"error_type":"technical","duplicate_webhook":true,"concurrent_duplicates":true}'
```

| Поле | По умолчанию | Значение |
| --- | --- | --- |
| `failure_rate` | 0 | Вероятность отказа от 0 до 1 |
| `error_type` | technical | technical, moderation или payload |
| `sync_mode` | normal | normal, 503 или timeout |
| `delay_min`, `delay_max` | 2, 20 | Диапазон задержки вебхука в секундах |
| `duplicate_webhook` | false | Две последовательные доставки |
| `concurrent_duplicates` | false | Две одновременные доставки |
| `no_webhook` | false | Не присылать вебхук |

Настройки фиксируются при приёме задания. Для позднего результата задайте
задержку больше `PROVIDER_TIMEOUT`. Для сброса настроек отправьте `{}`.
Очередь вебхуков тоже хранится в базе; неудачная доставка повторяется через
две секунды, а после падения отправителя восстанавливается по аренде.

| Переменная сервиса | По умолчанию |
| --- | --- |
| `PROVIDER_TIMEOUT` | 60 секунд с первого захвата отправки |
| `HTTP_TIMEOUT` | 5 секунд для сетевых операций HTTPX |
| `DISPATCH_LEASE` | 10 секунд |
| `POLL_INTERVAL` | 1 секунда |

Обязательно `HTTP_TIMEOUT < DISPATCH_LEASE < PROVIDER_TIMEOUT`. Для быстрого
ручного эксперимента можно запустить compose с `HTTP_TIMEOUT=1`,
`DISPATCH_LEASE=2`, `PROVIDER_TIMEOUT=5`, а провайдеру задать задержку 8 секунд.

## Тесты

Полный набор, включая настоящий HTTP-сервис с четырьмя воркерами:

```sh
docker compose up --build -d
docker compose --profile test run --rm --build tests
```

Тесты доменной логики используют отдельную базу `generation_test` и очищают
только её. Имя этой базы проверяется: оно должно заканчиваться на `_test`.
Проверка миграций откатывает и заново создаёт схему в этой тестовой базе.

E2E-тесты обращаются к работающему compose, создают уникальных пользователей
и временно изменяют настройки фейков, восстанавливая их после теста. Поэтому
их следует запускать последовательно на локальном стенде без ручных заказов;
тестовые пользователи и их журнал остаются в основной базе. Одновременный запуск
двух экземпляров набора не поддерживается.

Для локальной разработки нужны Python 3.12+ и `uv`:

```sh
uv sync --frozen
docker compose up -d db
uv run alembic upgrade head
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
uv run mypy app migrations
```

Без `TEST_SERVICE_URL` E2E-тесты пропускаются. Для полного локального прогона:

```sh
TEST_SERVICE_URL=http://localhost:8000 uv run pytest -q
```

Обязательные сценарии проверяются и на PostgreSQL с управляемой доставкой,
и через настоящий HTTP: 20 одинаковых оплат → одно начисление; 10 отказов
последней ноги → один возврат; успешная вторая нога после отказа первой;
поздний результат после срабатывания сторожа.

Дополнительно проверяются лимит активных задач, недостаточный баланс при гонке,
фильтрация референсов, модерация, payload, 503, HTTP-таймаут, молчание провайдера,
конкурирующие сторожа, ранний вебхук, восстановление аренды и откат транзакций.
В тестах дедлайн сдвигается в прошлое, чтобы не ждать минуту. E2E-тест позднего
результата затем дожидается реальной доставки фейковым провайдером.

Падение в критических точках проверяется исключением до commit и восстановлением
сохранённого состояния отправки. Эти тесты не завершают процесс сигналом SIGKILL.

## Миграции и структура

Схема создаётся только миграциями; `create_all` в приложении нет.
Первый revision создаёт таблицы и ограничения, второй добавляет каталог.

Применить миграции вручную в compose:

```sh
docker compose run --rm migrate
```

Добавить следующую миграцию при локальной разработке:

```sh
uv run alembic revision --autogenerate -m add_model_parameter
uv run alembic upgrade head
uv run alembic check
```

Сначала измените ORM-модель, затем проверьте сгенерированный revision, обе функции
`upgrade`/`downgrade` и перенос существующих данных. Миграции данных пишутся
явно через `uv run alembic revision -m add_catalog_model`. Старые применённые
revision не редактируются. Откат каталоговой миграции рассчитан на пустую базу:
при наличии заказов внешние ключи не позволят удалить использованные модели.

| Модуль | Ответственность |
| --- | --- |
| `main` | HTTP, проверка подписи, запуск и остановка фоновых циклов |
| `billing` | Журнал, платежи, блокировка пользователя, чтение баланса |
| `generation` | Создание заказа и единые переходы состояния |
| `workers` | Захват отправки, HTTP-клиент, восстановление и сторож |
| `fake_provider` | Настройки фейка, приём задания, доставка вебхуков |
| `models`, `schemas` | Таблицы PostgreSQL и контракты API |
| `config`, `db`, `security` | Конфигурация, соединения и HMAC |

Не используются регистрация, авторизация, настоящее хранилище файлов и деньги.
Для большого журнала чтение суммы можно заменить согласованной проекцией баланса,
но здесь единственный источник суммы делает финансовую логику проще для проверки.
